Operate

Operator API.

Everything under /api/manage/* is the platform operator surface: tenants, pricing, the archetype catalog, the demo, the audit log, and the schema reseed. It is protected by Cloudflare Access with full JWT verification, and answers JSON.

!
There is no UI for this yet.

Earlier revisions had a server-rendered panel at /manage with tenant tables, a pricing matrix and an archetype editor. The endpoints below are complete and are what that panel called, but nothing renders them — /manage in the app says so rather than showing a blank page. Drive them with curl through an Access service token, or build the views.

Authentication

These routes verify the Cf-Access-Jwt-Assertion header, falling back to the CF_Authorization cookie. Access sets both on requests it forwards, but the header can be stripped by a proxy or a custom domain config, and the cookie still carries a valid JWT.

  1. Cloudflare Access handles the login flow and issues a signed JWT.
  2. Verification: Concierge fetches the team’s JWKS, verifies the RS256 signature, checks the aud claim against CF_ACCESS_AUD and the expiry, and extracts the email claim.
  3. That email becomes the actor on every audit-log entry the request writes.

Anyone with a valid Access JWT matching your policy is authorized — there are no roles. Scope access with the Cloudflare Access policy itself. A failed check answers 403 access_required; the Worker logs which specific step failed (no token, missing env var, signature mismatch) so wrangler tail tells you why.

This is a different credential from the tenant surface: /api/manage/* does not accept a session cookie, and the rest of the API does not accept an Access JWT.

Endpoints

/api/manage/*Cloudflare Access required · JSON in, JSON out
EndpointWhat it does
GET /overviewThe authenticated operator’s email, the tenant count, and the same component health report /health returns — so the two surfaces can never disagree about what’s configured.
GET /tenantsEvery tenant. Takes ?q= for a case-insensitive search over email and id.
GET /tenants/{id}One tenant with its billing ledger (pruned and sorted), onboarding state, connected WhatsApp numbers, and recent audit entries.
POST /tenants/{id}/grant-repliesGrant credits. count must be positive; expires_in_days is optional and a non-positive value is treated as absent rather than as an instantly-expired grant.
DELETE /tenants/{id}Delete a tenant and everything keyed to it. Logged before the delete, because afterwards there is no tenant row to tie the entry to. Payment rows survive with tenant_id nulled.
GET /archetypesThe whole voice catalog including pending and rejected rows — that visibility is the point of the panel. Tenants only ever see approved ones.
PUT /archetypes/{slug}Create or replace a row. Requires label, description, voice prompt and greeting.
DELETE /archetypes/{slug}Remove a row.
GET /demoThe landing-page demo config, when its personas were last rolled, and the default generation prompt.
PUT /demoUpdate the config. The idle timeout is clamped to 5–600 s and the turn cap to 1–20, so a typo can’t lock visitors out or bake in a 24-hour window.
POST /demo/rerollRegenerate the demo personas now, against the current catalog and prompt.
GET /pricingCredit bounds, the per-(concept, currency) amounts, and the concept metadata (wire name, label, unit caption, whether the amount is milli-minor) so an editor doesn’t hardcode it.
PUT /pricingUpdate bounds and amounts. max_credits is capped at billing::MAX_CREDITS_CEILING — not a preference, but because the total is credits × milli price and a large enough max would overflow it.
DELETE /pricing/currency/{code}Drop every amount for a currency.
GET /auditThe audit log, 50 per page. Filters: actor, action, resource_type, and before as a cursor.
POST /reseedReapply the schema. Destructive, and gated a second time on ALLOW_SCHEMA_RESEED. POST only: a GET that wiped the database would fire on a browser prefetch.

The archetype catalog

The archetypes table is the platform-wide set of voices that both the tenant persona picker and the public demo read from. Each row carries a slug, label, description, the voice_prompt that becomes part of a tenant’s composed prompt, a greeting, suggested catch-phrases, off-topics, a never line, handoff conditions, and a safety verdict.

  • Every write resets the verdict. PUT /archetypes/{slug} sets safety_status back to pending and enqueues a SafetyJob keyed by slug. An operator editing a voice prompt must not inherit the old row’s approval.
  • Only approved rows reach tenants. The tenant-facing GET /api/archetypes and the demo both filter on it.
  • A write invalidates the demo. The rolled persona blob was generated from the old catalog, so it is dropped; the next visitor or cron tick regenerates it.
  • Audited: upsert_archetype and delete_archetype record the actor and the slug.
i
Referenced by slug, not snapshotted.

A tenant’s persona stores the archetype slug and layers their own fields over its voice prompt, so a catalog edit does reach existing tenants — and because the safety comparison is against the hash of the composed prompt, a tenant whose prompt changes underneath them has their AI replies paused until it is re-approved. Earlier revisions copied the row into the tenant instead; the default_rules_json column that copy carried went with the rule engine.

Audit log

GET /audit returns a chronological log of operator actions, newest first, 50 per page. Each entry records:

FieldDescription
actor_emailThe operator who performed the action, from the Access JWT’s email claim
actionWhat was done: grant_replies, delete_tenant, upsert_archetype, delete_archetype, update_demo_config, reroll_demo_personas, update_pricing, delete_pricing_currency
resource_typeWhat it affected: tenant, archetype, demo, pricing
resource_idThe specific identifier, where there is one
detailsJSON payload with action-specific detail
created_atTimestamp

Pass before with the oldest created_at you have to page backwards. has_more is true when the page came back full.

Setup

  1. In the Cloudflare dashboard, go to Zero Trust › Access › Applications.
  2. Create a self-hosted application with the path your-domain/api/manage* (no slash before the asterisk).
  3. Copy the Application Audience (AUD) Tag from the application overview.
  4. Set CF_ACCESS_TEAM (your team name) and CF_ACCESS_AUD as build environment variables, so they survive each deploy.
  5. Add a policy allowing the emails that should have operator access.
  6. Deploy.
i
Use /api/manage*, not /api/manage/* or /api/manage.

/api/manage/* leaves the bare endpoint exposed; /api/manage alone leaves every subroute exposed. Only /api/manage* covers both. Setting CF_ACCESS_AUD also disables the local dev bypass, so a production deploy can never activate it.

Locally

Access can’t reach localhost, so the dev server sets MANAGE_BYPASS_EMAIL and leaves CF_ACCESS_AUD empty. Both conditions must hold for the bypass to activate, which means a stray MANAGE_BYPASS_EMAIL in a production deploy is still blocked by the presence of the AUD. Run dev from the nix shell and the operator endpoints answer as that email.
