Architecture

Concierge is a Cloudflare Worker (Rust → WebAssembly) serving a JSON API, plus an Elm single-page app compiled to one static asset. All persistent state lives in Cloudflare D1 (metadata, billing, the archetype catalog) and KV (configs, sessions, conversation state). No message content is stored at rest.

The two halves

  • Worker owns: /api/*, the webhooks, the OAuth redirects, and the SPA shell. Nothing else.
  • Frontend owns: every user-facing string and every screen. It is an Elm Browser.application in frontend/, compiled by scripts/build-frontend.sh to public/app.js and served by Cloudflare's asset handler.
  • The shell: src/shell.rs renders one near-empty HTML document for every app route. It is produced by the Worker rather than shipped as public/index.html so there is a single code path for it and so the per-response CSP nonce can be stamped in. It carries no copy — every string is in the Elm app, and a second copy here would be the stale one.
  • Not server-side rendered. A crawler that doesn't execute JavaScript sees <div id="app"></div>, so the marketing routes are currently invisible to them. Deliberate trade; the fix is a build-time prerender of /, /pricing and /features into static assets, which needs no frontend change.
  • One bootstrap request. GET /api/bootstrap returns pricing, the demo config and persona catalog, and the session if there is one. The first frame after the spinner is the real page rather than a skeleton filling in four times.

API conventions

  • Envelope: success returns the payload at the top level. Failure returns {"error": {"code", "message"}} with a matching status. code is a stable machine string the frontend matches on; message is shown to the user verbatim. Without this the frontend would reduce a useful "Connect a WhatsApp number to continue." to a bare 400.
  • Auth is a cookie, and only a cookie. The SPA and the Worker are always same-origin, so the HttpOnly; Secure; SameSite=Lax session cookie set by /auth/callback rides along on every request. There is no token to store, attach or refresh, and nothing reads document.cookie.
  • Signed out is a status code, not a redirect. Any protected endpoint answers 401 unauthenticated. A redirect to a login page would hand the frontend HTML its decoder can't read; instead the app drops its session and renders the login screen.
  • CSRF: every state-changing request must carry X-Concierge-Request. A cross-site form post can't reach the API because the cookie is SameSite=Lax, and a custom header can't be set cross-origin without a preflight the Worker never grants. Checked before any handler runs, so a missing header can't be mistaken for a payload validation error. This replaced the per-tenant CSRF token the old HTML forms posted.
  • No caching: every API response is no-store. So is the shell, which carries a nonce; /app.js is the immutable part.
  • Redirect flows stay outside the API: Google OAuth (/auth/*), the WhatsApp Embedded Signup callback (/whatsapp/signup/*) and the webhooks all speak their counterparty's protocol.

Inbound channel

WhatsApp Business

  • Transport: Meta Cloud API webhooks at POST /webhook/whatsapp. Signature verified as HMAC-SHA256 over the raw body against META_APP_SECRET, compared in constant time.
  • Onboarding: WhatsApp Embedded Signup. The tenant attaches their own number to the platform's WhatsApp Business Account; the callback at /whatsapp/signup/* exchanges the code, reads the Meta user's identity, and can create the tenant if this is their first contact with us.
  • Tenant lookup: reverse index wa_phone:{phone_number_id} → WhatsApp account id → tenant id.
  • Outbound: Meta Graph API POST /{phone_number_id}/messages using the single platform token WHATSAPP_ACCESS_TOKEN. Nothing per-tenant is stored, so there is nothing per-tenant to seal or rotate — which is why the AES-256-GCM token encryption that earlier revisions carried is gone, along with ENCRYPTION_KEY.
  • Limits: no message-history endpoint, so post-hoc batching can't reconstruct text from older messages. See Reply buffer below.
i
Channels that were cut

Instagram DMs, the Discord relay and inbound email were each a full channel in earlier revisions, with their own webhooks, token storage and reverse indexes. They were removed to reach a launchable surface. The pipeline still dispatches on a Channel enum with one variant, so restoring one is a variant plus a match arm rather than re-plumbing the pipeline — but the adapters themselves are gone and would be rewritten.

AI reply pipeline

  • Inference binding: Cloudflare Workers AI AI binding. Default models: llama-4-scout-17b-16e-instruct for replies, llama-3.1-8b-instruct-fast for prompt-injection scanning and persona safety classification. Both configurable via AI_MODEL / AI_FAST_MODEL. The BGE embedding model went with the rule matcher.
  • Prompt envelope: every system prompt is wrapped by prompt::wrap(middle): a fixed PREAMBLE framing the model as a small-business reply assistant, the editable middle (the tenant's persona), and a fixed POSTAMBLE carrying house rules, jailbreak rails and the handoff sentinel [[HANDOFF]]. Both bookends are constants in src/prompt.rs; tenant content never reaches the model alone, and the API returns all three parts so the UI can render what-you-see-is-what-the-model-sees.
  • Persona prompt: tenant-wide, in PersonaConfig.source as one of two variants — Builder(PersonaBuilder) or Custom(String), never a blend, so there is exactly one source for the active prompt. The builder carries archetype slug, business name and type, city, hours, goal (free text + optional sanitized URL), catch-phrases, off-topics, a never line, and handoff_conditions; personas::generate renders these into the middle. Curated archetypes live in the archetypes D1 catalog and are referenced by slug for their voice prompt, with the tenant's own fields layered over.
  • Reply config: per-channel ReplyConfig { enabled, response, wait_seconds }. response is Canned { text } (sent verbatim, free) or Prompt { text } (appended to the persona and run through the LLM, one credit). The ordered rule list with keyword and embedding matchers, and the per-rule ApprovalPolicy, are gone; the field is deserialized with alias = "default_rule" so existing records still load.
  • Persona safety gate: AI replies are blocked unless the tenant's persona is Approved and its hash hasn't drifted since the last vetting. Canned responses are unaffected. See Persona safety queue below.
  • Final prompt: prompt::wrap(persona.active_prompt() + "\n\n" + instruction). Recent (role, content) turns from the conversation session, capped by max_history_messages, are passed as prior turns; the latest inbound is the final user turn. An empty history degenerates to a single-turn call.
  • Risk gate: src/risk.rs runs four pure, synchronous checks on the generated draft — length bounds (8–600 chars), money words, commitment words, and drift into the persona's own off-topics or never line. No model call, no I/O. A draft that trips any of them is not sent: the customer receives prompt::RISK_GATE_HOLDING_REPLY, the conversation enters handoff, the tenant is emailed with the reason, and a row is logged with action handed_off. The credit is not refunded, because the model ran. Always on — there is no per-rule policy and no ALLOW_NO_GATE override any more.
  • Handoff sentinel: every model reply passes through prompt::detect_and_strip_handoff before leaving the worker. A case-insensitive match strips the token and flips the session into the holding-pattern path.
  • Injection scan: bodies are truncated to 1000 chars, then a fast classifier checks for instruction-override patterns. A rejected message skips the entire pipeline: no reply, no credit.
  • Billing: only the AI reply step deducts a credit. Canned responses, the injection scan and safety classification are free. Deduction is optimistic (before the call) and restored on generation or send failure. Operators can grant credits per tenant through the operator API.
  • Pricing: a flat per-AI-reply rate, no tiers. The unit price in milli-minor units per currency lives in the singleton pricing_config row, operator-configurable.

Conversation sessions & handoff

  • Session record: Session in src/types.rs, persisted to KV at convsession:{tenant}:{channel}:{sender}. Holds a stable conversation_id, last_inbound_at, a bounded messages: Vec<ConversationMessage>, and an optional handoff: Option<HandoffState>. The convsession: namespace is distinct from the auth session: prefix.
  • Idle gap: ConversationConfig::idle_gap_mins (default 6 h). If now - last_inbound_at > idle_gap, the pipeline mints a fresh conversation_id, clears messages, drops handoff, and writes the new session.
  • History cap: max_history_messages (default 20) bounds messages. Inbound and sent assistant turns are appended; a withheld draft is not, so it can't poison the next call.
  • Handoff cooldown: handoff_cooldown_mins (default 60). Entering handoff — by sentinel or by risk gate — sets handoff = Some(HandoffState { signaled_at, notified }) and swaps the persona for prompt::HOLDING_PATTERN_MIDDLE for the cooldown. Past it the worker stays silent until the idle gap fires.
  • Tenant page: src/escalations.rs sends exactly one email per handoff, naming the channel, sender, an excerpt clamped to 200 chars, and — when the risk gate fired — which signal tripped. Email is the only channel; the Discord embed with Approve/Reject buttons went with the approval queue. Guarded by HandoffState::notified, and honouring the tenant's handoff_email opt-out.
  • Stamping messages: the D1 messages table carries a nullable conversation_id with an index, stamped on outbound rows and updated on the inbound row once the conversation resolves. Canned-only flows leave it NULL — those threads don't enter the conversation machinery.

The interactive demo

  • Endpoints: the persona catalog arrives inside GET /api/bootstrap (resolved server-side: warm KV cache → cold-miss regeneration against D1 + the LLM → empty), and POST /api/demo/chat runs one multi-turn call against the picked persona and the client-supplied history.
  • Statelessness: the client keeps the transcript and posts it each turn. Handoff round-trips as {handoff: bool} on the wire and a field in the Elm model; picking another persona resets it. No KV session, and the server keeps nothing.
  • Same envelope, same gates: the handler wraps the persona with prompt::wrap, refuses any archetype that isn't safety-approved, runs the same injection scanner, and honours the same sentinel. View the prompt renders the exact middle being sent.
  • Rate limiting: a per-IP hourly cap and a global per-UTC-day cap, both in KV. The global cap bounds worst-case model spend even under IP rotation; the per-IP check runs first so a caller already over their own limit doesn't drain the shared budget on a request we'd refuse anyway.

Persona safety queue

  • Trigger: PUT /api/persona and PUT /api/wizard/persona compute sha256(active_prompt()) on save; if it differs from safety.checked_prompt_hash, status flips to Pending and a SafetyJob { target, prompt_hash } goes onto the SAFETY_QUEUE producer binding. A save that doesn't change the composed prompt keeps the existing verdict, so the badge doesn't flicker. PUT /api/manage/archetypes/{slug} does the same for a catalog row.
  • Ordering: the enqueue happens after the save. A lost enqueue leaves the persona Pending, which is the safe direction; a successful enqueue against an unsaved persona would approve a hash nobody has.
  • Consumer: #[event(queue)] in src/lib.rs dispatches to safety_queue::handle_batch. Each job re-reads the target, drops itself if the hash has drifted (a newer save has already enqueued), runs safety::classify_persona against the fast model, and writes back Approved or Rejected { vague_reason } with checked_prompt_hash and checked_at.
  • Classifier: the system prompt enumerates the content policy (no incitement, harassment, discrimination, sexualization of minors, self-harm, illegal-activity promotion, unconsented impersonation) and the model returns strict JSON. The category is logged for abuse review but never returned; the user-facing text comes from a fixed mapping, so a prompt can't be iterated against the classifier.
  • Failure mode: classifier or KV failures call message.retry(); after 3 retries the job lands in concierge-safety-dlq. While Pending, AI replies are blocked and canned replies still send.

Localization

  • Locale model: every tenant carries a BCP-47 tag (Tenant.locale, e.g. en-IN, en-US) and an independent currency override. src/locale.rs::Locale bundles the two.
  • Resolution chain (first hit wins): tenant-stored locale → Accept-Language (parsed via the accept-language crate, intersected with the supported set) → cf-ipcountry mapping (IN → en-IN, else en-US) → hardcoded en-IN. Returned in /api/bootstrap.
  • Formatting is the frontend's job. The API returns amounts in minor units (paise, cents) or milli-minor units for the per-reply rate, plus an ISO 4217 code; frontend/src/Format.elm renders them. Indian digit grouping is implemented there and unit-tested, because ₹1,00,000 and ₹100,000 are both plausible renderings of the same integer and only one reads as one lakh.
  • Pure Elm, not Intl.NumberFormat. Formatting happens during view, and a port is asynchronous — the number would arrive a frame after the markup needing it. Two currencies and one grouping rule don't justify that.
  • What this replaced: icu4x (FixedDecimalFormatter with compiled_data), rusty-money for ISO 4217 metadata, and fluent-bundle with FTL files baked in via include_str!. All four dependencies are gone, along with src/i18n.rs and assets/locales/. UI copy lives in the Elm app.
  • Out of scope: AI-generated reply content stays English regardless of UI locale.

Reply buffer (Durable Object)

  • Class: ReplyBufferDO in src/durable_objects/reply_buffer.rs; binding REPLY_BUFFER.
  • Keying: one DO instance per {tenant_id}:{channel}:{sender} conversation.
  • Sliding window: each push appends to a pending list and resets the alarm to now + wait_seconds. Bursts collapse into one alarm fire.
  • Drop-after-send: the alarm handler clears DO storage before calling the LLM. Bodies live in DO state for ≤ wait_seconds (5 s default), then are gone.
  • Bypass: wait_seconds = 0 skips the buffer for instant replies.
  • ApprovalsDO is gone. A second Durable Object fanned out server-sent events to open approval pages. wrangler.toml carries a v3 migration with deleted_classes so Cloudflare drops the class; removing only the binding would leave it orphaned and the deploy would be rejected.

Storage layout

D1 tables

  • tenants: id, email (UNIQUE), facebook_id, plan, locale, currency, verified_at.
  • messages: unified inbound/outbound metadata (channel, direction, sender, recipient, action, conversation_id). No body content. Indexed on tenant+time, channel+tenant+time, channel_account_id, and conversation_id+time so a thread can be reconstructed for audit. Action is auto_reply or handed_off.
  • whatsapp_messages: channel-specific log. The instagram_messages, email_messages and email_metrics tables went with those channels.
  • tenant_billing: credit ledger as JSON, entries carrying optional expiry.
  • payments: Razorpay event log, kept for dispute and tax records. A deleted tenant's rows survive with tenant_id nulled.
  • audit_log: operator-action history.
  • archetypes: the curated voice catalog (slug, label, description, voice_prompt, greeting, catch-phrases, off-topics, never, handoff conditions, safety columns). Managed through /api/manage/archetypes; read by the persona picker and the public demo. Every write resets safety_status and enqueues a SafetyJob; only approved rows reach tenants. The default_rules_json column went with the rule engine.
  • pricing_config + the per-(concept, currency) amount table: operator-configurable pricing.

KV keys

  • session:*: auth sessions (TTL 7 d). The csrf:* keys are gone — the API uses a request header instead.
  • whatsapp:{id}: per-resource config, embedding its own ReplyConfig.
  • tenant:{tenant}:whatsapp:{id}: per-tenant index (empty value; existence is the index).
  • wa_phone:*: webhook → tenant reverse index.
  • wa_signup_state:*, wa_pubsignup_state:*: one-shot Embedded Signup nonces (TTL 10 min).
  • onboarding:{tenant}: wizard state. Holds BusinessInfo, the PersonaConfig (source variant + safety status), NotificationConfig, the ConversationConfig knobs, default_wait_seconds, and the completed flag that seals the wizard.
  • convsession:{tenant}:{channel}:{sender}: per-customer conversation session.
  • demo:*: the rolled demo-persona blob and its config; ratelimit:demo:* for the two caps.
  • Gone: instagram:*, ig_page:*, instagram_token:*, email_domain:*, email_rules:*, email_reverse:*, email_addrs:*, email_verify:*, discord_guild:*, discord_config:*, conv:{id}, csrf:*.

Auth

  • Login: Google OAuth only. /auth/login redirects straight to Google's consent screen — there is no login page to render, because the Elm app renders that and links here. /auth/callback exchanges the code, finds or creates the tenant, sets the session cookie, and redirects to /.
  • Where you land: decided in one place — the session's destination field, computed server-side from whether onboarding is sealed. The callback always returns to / and the frontend routes from there, so the rule isn't duplicated between the Worker's redirects and the app.
  • Facebook Login is gone as a sign-in method; it existed for Instagram. Meta identity still arrives through WhatsApp Embedded Signup, which does its own token exchange and can create a tenant the same way.
  • Session: a 7-day HttpOnly; Secure; SameSite=Lax cookie holding an opaque token that resolves to a tenant id in KV. Secure is dropped on http origins so plain wrangler dev still authenticates.
  • Dev shortcut: POST /auth/dev-login mints a session for an arbitrary email without a round-trip to Google, which can't reach localhost. Gated on dev_bypass::active; production sets CF_ACCESS_AUD, so it 404s there.
  • Operator API: /api/manage/* is protected by Cloudflare Access — the Cf-Access-Jwt-Assertion header (or the CF_Authorization cookie) is verified as RS256 against the team's JWKS, and the email claim becomes the actor in the audit log.

Outbound APIs Concierge calls

  • Meta Graph API for WhatsApp messaging and Embedded Signup.
  • Google OAuth token and userinfo endpoints for sign-in.
  • Razorpay API for orders, payment-signature verification and refunds.
  • Cloudflare Workers AI binding (a direct binding call, not HTTP): reply generation, injection scanning, safety classification.
  • Cloudflare Queues binding (SAFETY_QUEUE) for persona safety jobs.
  • Cloudflare Email Service binding (EMAIL) for handoff notifications.
  • The Cloudflare Access JWKS endpoint, for operator-API verification.

Limits and known constraints

  • No server-side rendering. Marketing routes are invisible to crawlers that don't run JavaScript. The fix is a build-time prerender; it needs no frontend change.
  • The operator API has no UI. /api/manage/* is complete, but /manage in the app says so rather than rendering a panel.
  • WhatsApp has no message-history API, so the reply buffer relies on its own DO state to reconstruct bursts.
  • Cloudflare Email Service requires sender domains to be onboarded in the dashboard before sends succeed. Handoff emails come from one fixed address, so this is a one-time step.
  • No per-message body storage. A conversation web-view would need a schema change and a privacy-policy update.
  • A custom prompt is capped at prompt::MAX_CUSTOM_PROMPT characters; anything past it is truncated on save.
