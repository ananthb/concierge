Architecture

How it works.

Concierge is one Cloudflare Worker. A WhatsApp message arrives on a webhook, is normalized into a single struct, and walks one pipeline that ends in exactly one of three outcomes: a canned reply, an AI reply, or nothing sent and a person paged.

The pipeline

Everything is normalized into an InboundMessage (channel, sender, recipient, tenant, metadata) before any logic runs. Channel handlers exist only to translate a webhook into that struct and to dispatch the outbound reply. WhatsApp is the only channel today; the pipeline still dispatches on a Channel enum, so adding one back is a variant plus an arm rather than a re‑plumb.

  1. The webhook arrives

    Meta POSTs a signed payload to /webhook/whatsapp. The signature is verified against META_APP_SECRET with a constant‑time comparison before the body is looked at.

  2. Normalize into InboundMessage

    Channel, sender, recipient, tenant ID, and channel‑specific metadata. From here every code path is identical.

  3. Log metadata to messages

    An append‑only row in D1: channel, direction, sender ID, recipient ID, tenant, timestamp. Message content is never persisted — only that something happened, with whom.

  4. Batch the burst

    Inbound messages are held for wait_seconds (default 5) in a Durable Object keyed by tenant + channel + sender. Three short messages typed in a row become one considered answer instead of three. Setting it to 0 replies immediately.

  5. Scan for injection

    The body is truncated to 1000 characters and run past a fast classifier. An injection attempt is dropped silently — no reply, no credit.

  6. Resolve the conversation session

    Per‑customer threads live in KV at convsession:{tenant}:{channel}:{sender}. If the customer has been silent longer than idle_gap_mins (default 6 h) a fresh conversation begins: new conversation_id, history cleared, handoff state wiped. Otherwise the existing session loads and the inbound is appended.

  7. Build the prompt envelope

    The system prompt is always a sandwich: a fixed preamble framing the model as a small‑business reply assistant, the editable middle (the tenant’s persona, goal and handoff conditions), and a fixed postamble carrying house rules, jailbreak rails and the handoff sentinel. Preamble and postamble are constants in src/prompt.rs; tenant content never reaches the model alone.

  8. Generate — canned text or a multi‑turn LLM call

    A canned response sends verbatim, no credit. A prompt response runs the reply model with the envelope as the system message and up to max_history_messages recent turns (default 20) as prior context. One credit is deducted before the call and restored if generation or send fails. AI replies are blocked entirely unless the persona’s asynchronous safety check has approved the current prompt.

  9. Gate the draft

    Two checks, in order. The risk gate withholds a draft that quotes a price, makes a commitment, strays past the persona’s boundaries, or comes out a suspicious length. Then the reply is scanned for the [[HANDOFF]] sentinel, which the model emits when it wants a person itself. Either way the conversation enters handoff and the tenant is emailed once.

i
Storage note

The messages table stores only metadata: channel, direction, sender ID, recipient ID, tenant, timestamp. No subjects, no bodies, no attachments. Replies are generated from in‑memory data and discarded. Recent conversation turns do live in KV, because multi‑turn context needs them; they are cleared by the idle gap.

The risk gate

This is the part of Concierge that matters most and is easiest to miss: a draft the gate dislikes is never sent to the customer at all. There is no review queue to approve it from, and no setting to turn the gate off.

The checks are pure and synchronous — no model call, no I/O — and run on the generated draft, not the customer’s message:

What trips itsrc/risk.rs · always on
SignalFires when the draft…
Lengthis under 8 or over 600 characters. Both ends correlate with a model that has lost the thread.
Moneymentions a currency symbol, or the words price, quote, refund, discount, free, cost.
Commitmentsays guarantee, promise, confirmed, booked, or names a day (“by Friday”, “by tomorrow”).
Persona driftcontains one of the tenant’s own off‑topics or their never say phrase.

When one fires: the customer gets a single fixed sentence saying a colleague will reply shortly, the conversation enters the handoff path, and the tenant is emailed with the reason that tripped it. The credit is not refunded — the model did run. The withheld draft is not stored, and the row logged to D1 carries the action handed_off.

i
This replaced an approval queue

Earlier revisions held a risky draft for a human to approve, edit or reject — from a Discord embed with buttons, or a web page, with a 24‑hour expiry and a digest email. That queue is gone. The safety property is the same (a draft mentioning money cannot reach a customer unreviewed) but there is nothing to staff and nothing to expire.

WhatsApp auto‑reply

  1. Meta delivers the inbound message to POST /webhook/whatsapp, signed.
  2. Concierge looks up the WhatsApp account by phone number ID and loads its ReplyConfig: enabled or not, one response (canned text or an AI instruction), and a wait window.
  3. The body is truncated to 1000 characters and run past the injection scanner.
  4. A canned response sends verbatim, free. An AI response combines the persona with the instruction, deducts one credit, and runs the model — provided the persona is safety‑Approved.
  5. The draft passes the risk gate, or it doesn’t and the conversation is handed to you.
i
No rule engine

Each channel used to carry an ordered list of reply rules pairing a matcher (keyword substring, or BGE‑embedding cosine similarity over a written intent description) with a response. In practice the mandatory default rule handled nearly every message, so the list is gone and a channel now has exactly one response. The embedding model and the cosine matcher went with it.

Persona & safety check

  1. The tenant picks a voice during onboarding and can rewrite every field afterwards from /dashboard/persona: voice archetype, business name and type, city, opening hours, a goal (what to drive customers toward, plus an optional URL), catch‑phrases, off‑topic boundaries, a never say line, and handoff conditions. A power user can instead write a raw prompt; a persona is one or the other, never a blend.
  2. The archetypes are a platform‑curated catalog in D1, managed through the operator API and themselves safety‑checked. Tenants only ever see approved ones.
  3. On save the composed prompt is hashed. If the hash differs from the last‑vetted one, status flips to Pending and a SafetyJob goes onto the concierge-safety queue.
  4. The consumer re‑checks the hash (dropping stale jobs), runs the classifier, and writes back Approved or Rejected with a deliberately vague user‑facing reason — the classifier’s actual category is logged, never returned, so a prompt can’t be iterated against it.
  5. While Pending or Rejected, AI replies are blocked tenant‑wide. Canned replies keep going out. Because the comparison is against the hash of the current prompt, an edit cannot slip past a stale approval.

Conversations & handoff

Each customer×channel pair has a conversation session in KV holding a stable conversation_id, a bounded list of recent (role, content) turns, the timestamp of the last inbound, and an optional handoff sub‑state. The id is stamped onto matching rows in D1 so a thread can be reconstructed for audit without ever having stored its contents.

  1. Idle gap. Silence longer than idle_gap_mins (default 6 h) means the next inbound starts fresh: history clears, handoff is wiped, the persona replies normally. Six hours is long enough for a customer mulling a quote over lunch, short enough that next morning’s message is genuinely new.
  2. Multi‑turn context. Up to max_history_messages turns (default 20, roughly ten exchanges) go to the model as prior history. Only sent replies are appended — a withheld draft never enters the history it would otherwise poison.
  3. Two ways in. The model can ask for a person by ending its reply with [[HANDOFF]] on its own line, triggered by the postamble’s universal conditions (it doesn’t understand; the customer asks for a human; the message touches medical, legal, financial or safety territory) plus the persona’s own. Or the risk gate withholds a draft. Both land in the same state.
  4. Holding pattern. The sentinel is stripped before the customer sees anything. For follow‑ups within handoff_cooldown_mins (default 60) the persona is replaced by a calm “a person has been notified” voice. Past the cooldown the worker goes silent until the idle gap resets the conversation.
  5. One page, by email. The tenant is emailed once per handoff, naming the channel, the sender, an excerpt, and — when the risk gate fired — which signal tripped. Guarded by a notified flag so extra customer turns inside the window don’t re‑send it.

All three knobs (idle_gap_mins, handoff_cooldown_mins, max_history_messages) are per‑tenant, with a cross‑field invariant: the idle gap must exceed the handoff cooldown, or an active handoff could be wiped before its cooldown ended. Empty values fall back to the in‑code defaults.

The interactive demo

The landing page hosts a live chat so visitors can see the model work without signing up. It’s framed explicitly: the visitor roleplays as a customer of a sample business and watches the reply arrive. Real customer messages arrive on WhatsApp — the demo chat box is never a customer surface.

  1. GET /api/bootstrap carries the demo config and its persona catalog alongside pricing, so the page needs one request to render. Personas are resolved server‑side (warm cache → cold‑miss regeneration → empty) and the client never generates or fetches them itself.
  2. The composer posts to POST /api/demo/chat with the persona slug, the turns so far, and a handoff flag. The server is stateless here; the client carries the conversation.
  3. The handler runs the same prompt envelope and reply model the production pipeline uses, gates on the same safety classifier, and honours the same sentinel. View the prompt reveals the exact middle being sent — the product is a prompt envelope, so letting people read it is the demo.
  4. Three limits, all operator‑configured: a per‑IP hourly cap and a global daily cap bound worst‑case model spend; a turn cap and an idle timeout swap the input for a sign‑up prompt.

Billing

Each AI reply deducts one credit. Canned replies, the injection scan and persona safety checks are free. Credits are deducted before the call and restored if generation or send fails — but not when the risk gate withholds a draft, because the model did run. At zero, AI replies stop and canned replies keep going. Credits are bought through Razorpay in any quantity, or granted by an operator.

What it runs on

  • Cloudflare Worker: Rust compiled to WebAssembly. Serves the JSON API, the webhooks, the OAuth redirects, and the SPA shell.
  • Elm: the frontend, compiled to one public/app.js served as a static asset.
  • Cloudflare KV: tenant and account configs, sessions, conversation state, persona, the archetype cache.
  • Cloudflare D1: message metadata, billing, payments, the archetype catalog, audit log.
  • Cloudflare Workers AI: reply generation, prompt‑injection scanning, persona safety classification.
  • Cloudflare Queues: the persona safety classifier (concierge-safety + its dead‑letter queue).
  • Cloudflare Durable Objects: the reply buffer that batches quick‑fire messages.
  • Cloudflare Email Service: outbound handoff notifications. Nothing is received by email.
  • Razorpay: credit purchases and the sign‑up verification charge.
