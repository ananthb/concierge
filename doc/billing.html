Billing & credits.

Concierge uses a prepaid reply credit system. Every AI reply deducts one credit from the tenant's balance. Canned replies are free, however many go out, and a draft the risk gate withholds is not refunded — the model ran. When credits reach zero, AI replies stop silently and canned replies keep going.

How credits work

  • Each tenant has a TenantBilling record holding a credit ledger — a list of entries, each with an amount, a source, and an optional expiry — plus a lifetime replies_used counter.
  • Credits are deducted before the reply is sent (optimistic deduction).
  • If AI generation or the message send fails, the credit is restored. An empty reply from the model restores it too.
  • A draft the risk gate withholds does not restore the credit. The model ran and produced text; the decision not to send it is downstream of the spend.
  • One AI reply is one credit, however much chat history was fed to the model. The multi‑turn context (capped by max_history_messages) sharpens the answer without multiplying the bill.
  • Canned responses, prompt‑injection scanning and persona safety classification are free — only the reply‑model call deducts. Holding‑pattern turns inside the handoff cooldown are still AI‑generated and still cost one each; once the worker goes silent past the cooldown, nothing further is spent.
  • Reading the balance prunes expired entries and re-sorts the ledger soonest‑expiring‑first, which is the order credits are consumed in, and persists the pruned form rather than recomputing it on every read.

Getting credits

Two ways.

1. Operator grants (free)

Platform operators can grant credits to any tenant through the operator API (POST /api/manage/tenants/{id}/grant-replies), optionally with an expiry. Useful for onboarding, promotions and support. Every grant is written to the audit log with the actor’s email.

2. Paid top-ups (Razorpay)

Tenants buy credits with a slider on the dashboard’s Credits tab: any quantity between the operator-configured bounds (default 1,000 to 1,000,000). No tiers, no packs, no subscription.

The per-reply rate is stored per currency in milli-minor units — 1/1000 of a paisa or cent — so a sub-paisa price fits. ₹0.10 per reply is stored as 10000. Operators change it without a code change.

Razorpay integration

  1. The tenant picks a quantity and presses Pay. The frontend calls POST /api/billing/checkout, which creates a Razorpay order server-side and returns the order id, the amount in minor units, the currency, and the publishable key id. The key secret never leaves the Worker.
  2. The frontend opens Razorpay’s hosted checkout with those parameters. This is the one place the app talks to JavaScript outside itself: the checkout is a modal their own SDK opens, so there is no redirect-only flow to use instead.
  3. On completion the frontend calls POST /api/billing/verify, which checks the HMAC-SHA256 payment signature and grants nothing. It exists to confirm the payment is genuine and to flip the tenant’s verified_at flag, so a user returning from checkout doesn’t have to race the webhook.
  4. Razorpay sends payment.captured to POST /webhook/razorpay. This is what grants credits. It verifies the webhook signature, credits the ledger, and records the payment in the payments D1 table.
!
The webhook is not optional.

Credits are granted by the webhook and by nothing else. A deploy where the webhook is misconfigured will take payments and grant no credits — and the tenant-facing verify call will happily report success, because a valid signature is all it checks. The split is deliberate: a forged client call cannot mint credit. Configure the webhook before you charge anyone.

Required secrets

  • RAZORPAY_KEY_ID: API key id. Also returned to the browser — it is the publishable half.
  • RAZORPAY_KEY_SECRET: API key secret. Server-side only.
  • RAZORPAY_WEBHOOK_SECRET: for verifying webhook signatures.

The sign-up verification charge

The onboarding wizard will not finish on a metered plan until a Razorpay payment has been captured for the tenant. A small charge (operator-configurable per currency) is taken through POST /api/billing/verification, which tags the order with kind=verification; the webhook records the capture, flips verified_at, and auto-refunds it.

This is the abuse gate for fresh sign-ups: it proves a working card without charging for anything. Complimentary (non-metered) accounts skip it entirely and cannot buy credits.

Pricing management

Operators set the global rates through GET / PUT /api/manage/pricing. One flat rate per currency — no tiers, no packs. Prices are stored per currency in that currency’s own units; there is no exchange rate and no conversion.

The schema is two tables:

  • pricing_config: singleton (id = 1) holding the currency-agnostic settings min_credits (default 1,000) and max_credits (default 1,000,000).
  • pricing_amount(concept, currency_code, amount): one row per (concept, currency) cell. Currency codes are ISO 4217. The unit is determined by the concept and is the same for every currency.
ConceptUnit (every currency)Used by
unit_price_millimilli-minor (1/1000 of paise / cent / …)The per-AI-reply rate. Stored fine-grained so sub-minor prices fit (₹0.10 = 10000).
verification_amountminor unitsThe sign-up verification charge, auto-refunded.

An address_price concept existed for the reply-email packs and went with the email channel. Rows for it are harmless if your database still carries them; nothing reads them.

GET /api/manage/pricing also returns the concept metadata — wire name, label, unit caption, and whether the amount is milli-minor — so an editor renders the table without hardcoding it, and a new concept appears without a frontend change. max_credits is capped at billing::MAX_CREDITS_CEILING; that is not a preference but an overflow bound, since the order total is credits × milli price.

Currency symbols are rendered by the frontend (frontend/src/Format.elm), which also implements Indian digit grouping — ₹1,00,000 is one lakh, and ₹100,000 is a bug that still looks like a number. The rusty_money crate that used to supply ISO 4217 metadata server-side is gone with the rest of the server-rendered templates.

Every pricing edit writes an update_pricing entry to the audit log.

Billing state

Each tenant’s billing state is a JSON ledger:

{
  "credits": [
    { "amount": 100,  "source": "grant",     "expires_at": "2026-10-31T23:59:59Z" },
    { "amount": 8350, "source": "purchased", "expires_at": null }
  ],
  "replies_used": 1550
}

Purchased credits never expire. Granted credits may, and are spent first — the ledger is sorted soonest-expiring-first, so an expiring grant is consumed before a permanent balance rather than stranded behind it.
